# Frontend contract

1. Two surfaces: a landing page at / and the product at /app. The landing page is a required deliverable, not a stretch goal. Its sections are hero, problem, how it works, proof, a button into /app, and a footer with the repo link, with real copy drawn only from the brief and README. There is no demo-video section on the landing page (builder's decision, 2026-11-13); the demo video lives in the README, the submission and the X post.
2. UI code in the plans is structural only: semantic markup, routing, state and data. No custom colors, fonts, shadows or animation. All visual design happens in the Design pass, which uses the ui-inspiration skill (~/.claude/skills/ui-inspiration) as its source of truth for design references and tokens, so nobody invents a style before it.
3. Executors apply the plan's UI code exactly and do not style.
4. The Design pass runs the ui-inspiration skill, writes docs/design/direction.md (the references it used, the principles they share, the token set, and the product's own identity), builds / and /app only from the tokens in that file, and then checks every page against it.
5. Craft pass (builder's decision, 2026-11-13, after the first Design pass read as basic): the unslop skill (C:\Users\bamig\Documents\VIBE CODE\Hackathons\creator-skills\skills\unslop, by Damir Sokolovsky, CC BY 4.0) is run over / and /app after the Design pass. It audits the screens for the usual AI-UI tells, sets a direction, and fixes spacing, color, copy, type, layout, details, visuals and motion in order. Where unslop and direction.md disagree, the result is written back into direction.md so the two never diverge, and the tokens stay the only place design values live.
6. The build is not finished until the Design pass and the craft pass have run and every page has been checked against docs/design/direction.md.
7. Redesign (builder's decision, 2026-11-13, after two restyle-only passes were rejected): the structure is planned before it is built. A session first writes docs/design/UX_AUDIT_AND_REDESIGN_PROPOSAL.md in the manner of https://github.com/winsznx/rooq/blob/main/docs/UX_AUDIT_AND_REDESIGN_PROPOSAL.md (evidence and limits, findings with ids and priorities, a reference board with a boundary for each reference, visual direction, per-screen redesigns, component states, motion choreography, a surface coverage matrix, implementation order, acceptance evidence) and stops for the builder's approval; only then does it implement, in staged commits that each pass the checks. The hero is the real product as an interactive instrument; /app is an app shell with routes, an operations view and distinct loading, unavailable, empty and populated states. Rooq is a quality and structure reference, never a template to copy.
